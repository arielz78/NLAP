# Source Decision Sheet

**What this doc is:** the single source of truth for **per-source integration method + field inventory + verdict**. One job. It answers "for source X, what's the confirmed method, endpoint, what fields does it carry, and is it a PASS/DROP?"

**What this doc is NOT:** it does not own *decisions* (→ `Decision_Log.md`), *session narrative* (→ `Execution_Log.md`), or *release status* (→ `R5_Scope.md` snapshot). When a probe produced a decision, it's one-lined here and linked to the Decision_Log §.

**Structure:**
1. **Source Register** — the live reference table. Update rows in place; never goes stale.
2. **Per-Source Build Reference** — stable technical detail (endpoints, payloads, field maps, traps) for live + build-ready sources.
3. **Methodology** — the probe hierarchy + tier definitions (stable).
4. **Probe Log** — append-only chronological record of what was probed/found/overturned.

### AllEvents (live — Vaughan / Richmond Hill / Markham branches)
- `POST https://allevents.in/api/events/list`, body: `{"city":"vaughan","country":"canada","page":0,"rows":500,...}`. `rows=500` returns full set, no pagination at current volume. Three branches, one per city.
- **Response: top-level key is `data`** (not `events`).
- Field map: `eventname`→title · `start_time` (Unix)→StartDate · `end_time`→EndDate · `event_url`→Link · **`venue.name` always empty** → locationName = `full_address` segment before first comma · `venue.city`→geo-filter (CITY_MAP).
- Extracted to **discrete Candidates fields** (#72, 2026-06-23): `categories[]`→`SourceCategories` · `organizer.name`→`Organizer` · `score` (internal popularity)→`SourceScore`. **`DescriptionRaw` left empty** — the API carries no event description. Previously these were concatenated into `DescriptionRaw`, which let AllEvents win richest-wins survivorship on raw length and polluted the R6 content signal — see DL§51 follow-on.
- **⚠️ Found 2026-07-27 (#108) — descriptions EXIST on the HTML detail page; the API just doesn't carry them.** The "no event description" note above is true of `api/events/list` but **not of AllEvents**: an event whose API record has no description renders a full, rich "About the event" body on its own page (e.g. *Canada Day Family Glow Lab*, `allevents.in/vaughan/...`) — collapsed behind a **"View Details"** link once the event has ended. So the description is available at a cost of **one extra HTTP request per event** (~200–300/week), and was never fetched because the T1 API path was assumed complete. **Why it matters now:** AllEvents is ~40% of production, and R7-W6 has been sizing a *feature-poverty* problem — "~40% of label-deck rows have no real prose," the text-only ceiling the live editor sittings exist to measure, and a measured 30.9% include rate on category-block rows (vs 53.9% for AllEvents rows that do carry a description) — all of which may be artifacts of what we fetch rather than what exists. **✅ VERIFIED AT SCALE 2026-07-27 — it holds.** This is an upstream R1 fix, cheaper than compensating for the gap with model features. *(Note: the category blocks sitting inside `DescriptionRaw` in the R7 label deck are pre-#72 legacy residue; post-2026-06-23 AllEvents rows have `DescriptionRaw` empty.)*
- **#108 measurements (2026-07-27) — what a detail-page fetch actually buys.** The API carries **no description key at all** (`description` / `desc` / `about` / `summary` / `short_description` / `details` all absent across **392 live records** from the three city branches — not empty, absent). The page does: **20/20 currently-live events** yield a description (median **1,097** chars); **111/137 (81.0%)** of the R7 label deck's prose-gap AllEvents rows yield one (blank rows **88.7%**, category-block rows **75.6%**), median **908** chars, **88.3% longer than the 300-char `DESC_CHAR_CAP`**. Staging file (not wired in): `models/sectioning/deck/allevents_backfill_2026-07-27.json`. **Five implementation constraints, all learned the hard way — a fetch that ignores them corrupts data:** (1) **ended** events serve a stripped page unless the URL carries **`?ref=past-event-page`**; live events don't need it; (2) **`encodeURI()` the URL** — em-dashes in AllEvents slugs throw `Cannot convert argument to a ByteString`; (3) **verify the numeric event ID in the final URL matches the one requested — 3 of 137 (2.2%) silently redirected to a *different* event**; writing a redirected page's text onto the original row is a silent data-poisoning bug; (4) **retry once before recording a miss** — transient 410s succeed on retry; (5) **extract from the DOM container whose id/class contains "description"** — `og:description` is templated boilerplate (*"Find tickets & information for X…"*) and must never be accepted as a description; JSON-LD truncates at ~300 chars, second choice only. Polite delay ≥800 ms. Extracted text carries two strippable artifacts: the title duplicated at the head, and a trailing *"Also check out other … in …"* nav sentence. Misses are not random — 18 of the 22 genuine misses are template-generated corporate-training listings with no description on the page either.
- **⚠️ GEO INTEGRITY — found 2026-07-27 (#108 backfill), UNRESOLVED, own fix needed.** AllEvents' **`richmond-hill` city slug conflates Richmond Hill, Ontario with Richmond Hill, GEORGIA, USA.** The API's `venue.city` returns `"Richmond Hill"` for both, R1's `CITY_MAP` allowlist passes it, and nothing downstream looks again. **10 rows detected in the 456-row R7 label deck** (detection is incomplete — it requires description text to see, and only 137 rows had recovered text): confirmed by *"Richmond Hill, GA"*, *"Savannah Harley-Davidson"*, *"Bryan County Administrative Complex"*, *"Coastal Georgia Botanical Gardens"*. **Three of the ten carry a positive editor label** (rows 23 Couples / 166 Families / 174 Golden) — i.e. this is **label noise in the gate's positive class**, produced by feature poverty rather than editor error. This is the first known geo hole that the strict `CITY_MAP` allowlist does **not** close (contrast the Eventbrite gate, closed 2026-06-25 / #59), because the failure is an ambiguous city *name*, not a missing one. **The discriminator the API already returns is `full_address`** — a province/state or country test, not a keyword.

  **✅ FIXED 2026-07-27 (#109) — and the deck undercounted the leak by 5×.** A live pull of all three branches measured **51 of 396 records (12.9%) foreign**, against the 10 the deck showed — deck detection was low because it inferred geography from *description text*, which only 137 of 456 rows had. The leak is also **not only Georgia**: `richmond-hill` returns **Richmond Hill, NEW YORK** (Queens) as well, and the `markham` branch returns **Markham, ILLINOIS**. `venue.full_address` is populated on **390 of 390** records, so it is a reliable discriminator. **Fix applied to all three `AllEvents Normalize*` nodes** in `workflows/NLAP R1.json`: reject on *positive* foreign evidence (`, GA` / `USA` / `United States` …) **and never on a missing address** — a blank address is not a fact, and Stage 0 may act only on facts. The `!DOMESTIC_ADDRESS` guard is required because **`, CA` is both California and Canada**. Verified by executing the patched node code against live API data: **396 → 345, 51 dropped, 0 false drops** (the sole Markham drop is `15743 Crawford Avenue, Markham, United States` = Markham IL). ⚠️ **Requires an n8n re-import to take effect** — the repo JSON is fixed, the running instance is not. **Still open:** the 3 deck rows carrying a positive editor label, and a proper re-detection of the deck via `full_address` rather than description text.
- **Re-verified 2026-07-03 (folded into #63 sweep close-out):** `going.totalCount` no longer exists in the current API response — the field was removed upstream at some point since the 2026-06-23 audit; drop the "RSVP signal" note. `featured` is `true` on 100% of a 225-event sample — not a discriminating signal, contradicts the earlier "available, low priority" framing. **Captured 2026-07-03 (#84, trimmed schema — see Decision_Log §54 addendum):** `display_price_label` (AllEvents' own pre-formatted price string, e.g. `"CAD 30 to 49"`, `"Free"`, 141/223 populated — richer than the sparse `tickets{}` object, 2/223) → `CostRaw`; `tags[]` + `formats[]` merged into `categories[]` → `SourceCategories` (additive, not a replacement). Verified live (exec 503): 223 kept, 141/223 with CostRaw, 220/223 with SourceCategories. **Still parked, no consumer:** the raw `tickets{}` object (superseded by `display_price_label` as the richer signal).
- Build: `AllEvents Fetch` (HTTP POST, UA header) → `AllEvents Normalize` (geo + decodeEntities). Exec #440: 233 fetched → 154 in-window.

## 3. Methodology

### Probe hierarchy — work top-to-bottom, stop at first clean reliable data
1. **DevTools first** (Network → Fetch/XHR → reload) — catches admin-ajax plugins, REST-ish endpoints, dynamic sources. First move on anything dynamic.
2. **Main HTML document** (Network → Doc → Response) — catches server-rendered "SPAs" (VPL).
3. **Blind feed probe** — `/feed`, `/?feed=rss2`, `/?ical=1`, `/events.ics`, `/calendar.ics`.
4. **WP REST API** — `/wp-json/wp/v2/types` → registered post types → `/wp-json/wp/v2/{type}`.
5. **JSON-LD** in page source — `<script type="application/ld+json">`, `@type: Event` (TRCA pattern).
6. **HTML scraping** — known class names / structure (VPL, unionville).
7. **Headless browser** — last resort; only for high-value weekly sources with all above dead.

**Core lesson (2026-06-06):** a DROP is only as strong as the *surface* it was tested against. Three sources (VPL, visitvaughan, unionville) were initially written off, then automated via methods 1–2. **Always open DevTools before writing off a source; never generalize "this surface is dead" to "this source is dead."** Full standard in `scrape_blueprint.md`.

### Integration tier ranking — ease *and* transferability
1. **Direct JSON/REST API** — AllEvents, McMichael, visitvaughan, Eventbrite. Cleanest; one call, you control pagination/filters.
2. **JSON-LD** (schema.org) — standardized parsing → transfers to any schema.org site. (TRCA Black Creek, retired.)
3. **Embedded app-state JSON** (`__NEXT_DATA__` etc.) — clean to fetch but bespoke per framework; parser doesn't transfer. (Meetup, CityPlayhouse.)
4. **HTML-card scrape** via ajax/admin endpoints — works, zero infra, fragile + bespoke. (unionville, VPL.)
5. **Headless required** — worst tier. No current sources here.

Tiers 1–2 = reusable integration code (ports to client #2). Tiers 3–4 = one-off build every time. **The portable asset is the canonical Candidates schema + adapter contract** (each adapter = pure function `raw feed → canonical record`); hardcode Vaughan specifics (aggregator domains, geo-filter, endpoints).
