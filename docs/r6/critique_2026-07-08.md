## Root theme
Everything the doc calls **"the editor's revealed preference"** — labels, grounding, gates — is assumed
clean, and the doc's own evidence (§2c zero-filled `Score_Final` driving date-sort slots; §7.10's
~99%-at-New throughput) suggests it is not. The restraint architecture (§5, §6) is genuinely strong and
would survive senior review largely intact. The soft spot is concentrated in that one place. Resolve the P0
and define the pre-ship gate before opening issues; most of the rest is cheap to settle with data on hand.

## P0 — "Revealed preference" is contaminated by the pipeline's own defaults
Passive acceptance is indistinguishable from active choice in both the backtest labels and the few-shot grounding.

- **Lens:** applied ML / statistics / validation
- **Claim challenged:** §1 "replicates the editor's picks and order"; §4.1 backtest vs "the editor's slot order"; §3 few-shot examples = "the most recent editor-approved/locked picks."
- **Why weak:** Since the pipeline went live (~April 2026), slot order is machine-produced — `buildIssues.js` sorts `Score_Final` desc then `Start Date` asc, and §2(c) confirms every `Score_Final` is 0, so post-pipeline slot order **is earliest-date sort** unless the editor actively swapped. §7.10 says ~99% of supply sits un-reviewed at New, so an unknown, possibly large fraction of "editor-approved" picks/orders is un-reviewed pipeline output. Bites twice, asymmetrically:
  1. Post-pipeline backtest labels partially encode the **date-sort baseline R6 exists to replace** (and the struck recency signal, §30). A date-leaning scorer gets *rewarded* on those groups.
  2. Worse: few-shot grounding (§3) draws **exclusively** from post-pipeline picks ("only recent post-pipeline picks have raw-text rows") → 100% of the LLM signal's grounding comes from the most contaminated cohort. The scorer could imitate the pipeline's quota-filling, not the editor's taste.
  Also: for pre-pipeline issues, no one has verified slot order is a *preference* ranking vs chronological/layout convention (README §7 says "likely").
- **Threatens:** the imitation objective becomes partially self-referential; §3's grounding design and the primary backtest both need rework. The one finding that could force a redesign, not a retune.
- **Evidence needed:** (a) measure editor-touch rate on post-pipeline published picks (locks/swaps/edits are in Airtable — count them); (b) correlate historical slot order with start date, split pre/post-pipeline; (c) ask the editor "is slot 1 deliberately your strongest pick?"; (d) restrict few-shot positives to demonstrably editor-touched picks, or accept + document the contamination.

## P1 — No defined pre-ship gate
No baseline comparison, no thresholds; 2 of 3 signals plus all weights ship unvalidated.

- **Lens:** validation / statistics
- **Claim challenged:** §4.1 "Strong positive = the content signal reads like the editor"; §4.2 "Require positive, don't maximize"; snapshot "forward swap-rate = the real gate."
- **Why weak:** Frozen intent (roadmap W4 step 2) required the backtest to answer: does scoring **beat trivial date-sort** ("if it doesn't, simplify R6")? The scope silently drops that baseline. Without it, "strong positive" Spearman is uninterpretable (per-group n=5 is coarse; only the cross-issue mean carries info, and it needs a comparator). The doc concedes the backtest exercises only the LLM signal, and evaluates on distribution-shifted inputs (polished eval copy vs raw-text few-shot examples). Venue + source get no offline validation; hand-set weights have no stated grounding data (the roadmap grounded them in click facts — which §1 now forbids). Net: the "real gate" fires only after shipping live; pre-ship there is no numeric criterion. The roadmap's exit criteria ("client has reviewed one full scored issue and signed off") were superseded with nothing.
- **Threatens:** a scorer no better than date-sort ships; weeks of live swap-rate burned discovering it.
- **Evidence needed:** (a) add date-sort's Spearman-vs-editor-order as the mandatory baseline the hybrid must beat; (b) state numeric pass bars for backtest + floor; (c) note §7.6's accruing pool+pick snapshots enable a small *selection* sanity check pre-ship (pool-minus-picks lets the scorer's top-5 be checked against actual picks before launch).

## P1 — Swap-rate ("the real gate") is confounded
By anchoring and by unsecured editor participation; can trend down for reasons unrelated to imitation quality.

- **Lens:** validation / product
- **Claim challenged:** §4.3/§4.5 "swap-rate (fully powered) is R6's gate"; §7.6 overrides = "the counterfactual dataset #87 needs."
- **Why weak:** Swap-rate is measured on a ranking the scorer itself presented. Editors anchor to defaults; declining swap-rate is equally consistent with growing trust/disengagement (automation bias) as with improving imitation — and §7.10's own evidence says disengagement is the *likely* mode. "Fully powered" is true but beside the point: high power, unestablished *validity*. The doc catches the participation risk (no data if he doesn't review) but not the worse failure: **misleadingly good data if he reviews shallowly.** Also degrades §7.6 — presentation-biased counterfactuals are weaker fuel for #87 than implied.
- **Threatens:** R6 passes its only gate while imitating no one; #87's go/no-go rests on a biased dataset.
- **Evidence needed:** define what a *valid* swap-rate observation requires (evidence the editor actually reviewed — e.g., any touch event per issue as a review-occurred flag); pair with the §7.11 imitability-ceiling probe; secure the weekly review loop (§7.10) *before* treating the gate as meaningful.

## P1 — Cold-start degeneracy
At launch the two "cheap, stable" structured signals are likely near-uninformative → the hybrid is a de facto LLM ranker sold under a three-signal transparency story.

- **Lens:** data engineering / product-method fit
- **Claim challenged:** §3 "it discards the two cheap, stable, fully-transparent signals R5 just revived"; client pitch "source track record, venue track record, and a quality read."
- **Why weak:** The scope never defines how the source prior is computed, or from what data. Historical picks are pre-R5 Facebook/Eventbrite-heavy with 0% `Source` fill (407 legacy blanks, #69 open); ~11 of 13 current sources have essentially no editor-pick history → priors are guesses or uniform. Venue recurrence is "forward-only" (4% click overlap; no clean venue key in `issue_history.json`) → at ship it rests on a few weeks of post-R5 joins. If both structured signals are flat, the LLM signal decides everything and §3's anti-end-to-end-LLM rationale is rhetorical at launch. Compounding: the 2026-06-04 amendment's **client-curated trusted-venue list** (the venue cold-start salvage) has vanished from the scope with no disposition.
- **Threatens:** day-one behavior is an opaque LLM ranker in a formula costume; the client handoff explanation is materially inaccurate; weight tuning is meaningless over degenerate signals.
- **Evidence needed:** define the source-prior computation; measure entropy/coverage of both structured signals on the live pool at build time; disposition the trusted-venue list explicitly.

## P1 — The recency cut rests on *stated* preference
In a doc whose entire methodology forbids specifying from stated preference.

- **Lens:** statistics / product-method fit
- **Claim challenged:** §2/§6 "Recency struck (§30)… do not re-propose"; justification "the client said dates don't matter."
- **Why weak:** The PRE-R6 addendum's own rule (reinforced 2026-07-02) is "do not spec from stated criteria; ground in revealed preference." That discipline is applied everywhere *except* this cut, grounded purely in a client statement. No one measured whether the editor's actual picks/order track date proximity. If revealed preference includes date-nearness (plausible for an events newsletter), a "faithful imitator" with recency amputated has a built-in ceiling, and §3's "massive ties with no legitimate tiebreaker" is partly self-inflicted. The revisit condition (watch live swaps) defers to the most expensive evidence when the cheap offline test exists today. Must be measured on **pre-pipeline** issues (see P0).
- **Threatens:** systematic scorer-editor divergence surfaced weekly, misdiagnosed as LLM-signal failure.
- **Evidence needed:** correlate pre-pipeline picks + slot order against days-to-event. One afternoon.

## P2 — Forced-choice pairs used as both few-shot negatives AND the grading set
Leakage designed into the plan.

- **Lens:** applied ML / validation
- **Claim challenged:** §3 "Negatives: seeded by the 10 forced-choice pairs" vs §7.3 "graded against the 10 head-to-head pairs + held-out issues."
- **Why weak:** Same 10 pairs in the prompt and in the eval → the LLM-signal grade is contaminated (the exact leakage class §6 cites when rejecting the learned ranker). With ~3 negatives per section the temptation to double-use is strong; the doc doesn't forbid it.
- **Threatens:** an LLM signal that looks validated and isn't; the only pre-ship selection-shaped evidence becomes worthless.
- **Evidence needed:** one sentence in §3/§7 — pairs used as examples are excluded from grading; §7.4's ongoing collection replenishes whichever side is short.

## P2 — The click floor is uncalibrated
Its expected value under *perfect* imitation is unknown and may be indistinguishable from zero.

- **Lens:** statistics / validation
- **Claim challenged:** §4.2 "a faithful imitator only reproduces the editor's own 0.60→0.43 gradient."
- **Why weak:** The gradient is position-confounded (README §7). If mostly position effect, a perfect imitator's score-vs-click correlation could be ~0 → the floor flags a *good* scorer as "grossly wrong" (or passes a bad one; slot η²=4.3%, little separable signal either way). The reference point is measurable *now* — editor slot order vs `percentileVuc` on the frozen 924 is the perfect-imitator's floor score — but the doc doesn't compute it. Secondary: the frozen set's known bias (recurring/popular venues under-represented, README §5) blinds the floor exactly where venue-recurrence acts; §59's revisit trigger is framed as "too noisy" when the real failure mode is *bias*, with no diagnostic.
- **Evidence needed:** compute editor-order-vs-clicks correlation on the frozen set; set the floor's pass band relative to it, not to zero.

## P2 — "Scored once and stored" collides with dynamic few-shot rotation
A single issue ranks scores produced under different grounding sets.

- **Lens:** data engineering / applied ML
- **Claim challenged:** §3 "Scored once per candidate at R2 time and stored… stable run-to-run" alongside "dynamic few-shot selection at runtime."
- **Why weak:** An issue window spans candidates ingested across multiple weeks. Each week's ingests are scored under that week's example set (and accrued venue/source state), then compared against each other at allocation. Two identical events ingested two weeks apart can rank differently for reasons no one can explain to the client — the opacity §3 rejects the end-to-end LLM for. Logging the example set records the incomparability; it doesn't remove it. The revisit condition has no detection mechanism; swap-rate can't isolate it.
- **Evidence needed:** decide the epoch policy explicitly — pin the example set per calendar period and re-score the open window on rotation, or accept + document cross-week incomparability.

## P2 — Backtest grades a recency-grounded scorer against 15 months of drifting history
And drops the frozen intent's cohort-scoping rules.

- **Lens:** validation
- **Claim challenged:** §4.1 "per section-issue group on `issue_history` (77 issues)."
- **Why weak:** The few-shot grounding targets the editor's *recent* taste; the backtest averages over 15 months during which sections changed (Golden Age Readers didn't exist before March 2025) and taste drifted. A correct recent-taste imitator can score poorly on early cohorts, reading as failure. The roadmap's data-scoping rules (GAR March 2025+; Jan–Feb 2025 least-audited labels) don't appear in the validation design.
- **Evidence needed:** carry the cohort rules into §4.1; report the backtest by cohort (early/mid/recent), gating on recent.

## What this doc does not consider
- **The imitation target is a person, not a role.** Editor turnover / a second editor resets the grounding corpus, swap-rate baseline, and imitability ceiling. Nothing marks which artifacts are editor-specific.
- **Client-#2 cold start.** The transfer story is config extraction, but the real asset is the grounding *data* (issue_history, forced-choice pairs, source/venue history) — none exists for a new client. §1's "scored substrate" transfers architecture, not capability; the doc never says what R6-for-client-#2 minimally requires.
- **LLM model-version drift.** Stored `Score_Final` values computed under different model/prompt versions are incomparable, and the GPT-5-mini swap (§7.7 / Debt #13) is planned mid-stream. No versioning / re-score policy for the scores themselves.
- **Upstream classification noise.** Few-shot grounding + grading are section-scoped, but section labels come from R2's classifier — whose error rate is the entire reason R7 exists. Misclassified picks contaminate per-section grounding; unquantified.
- **Gameable inputs.** Event organizers author the exact text the LLM content-fit signal scores; a promoter who learns the newsletter uses automated selection can write to the scorer. Low likelihood, but the only signal an outsider controls end-to-end.
- **Venue-string stability over time.** The normalization pass (§2a) measured one 5-week snapshot. The recurrence signal's real dependency — the same venue emitting the same string across *months* and across *sources* — wasn't measured.
- **Within-issue A/B platform feasibility.** §4.5's power math sets #87's go/no-go bar assuming Beehiiv can split content arms per section within one send — never verified; if it can't, the bar is defined over an instrument that doesn't exist.
- **Quality-floor threshold has no ground truth.** "Set at build from the score distribution" (§3) presumes the distribution separates junk from non-junk with no labeled junk to check against; a percentile cut on a degenerate distribution is arbitrary.
